## 1. The problem
A package-lock.json generated on one OS/CPU can omit the platform-specific optional native packages (e.g. @rollup/rollup-linux-x64-gnu, @esbuild/linux-x64, @swc/core-*, lightningcss-*, sharp platform builds) needed on other platforms. `npm ci` on another OS then fails with "Cannot find module ..." or "Missing: ... from lock file", or silently skips the binary. See npm/cli issues #4828 and #8320. lockmatrix statically audits a lockfile and reports which platform-specific optional dependencies are missing and which target platforms (os/cpu/libc) are not covered BEFORE CI fails. Fully offline, read-only.

## 4. Behaviour (MVP)
CLI: `lockmatrix [path-to-lockfile-or-project-dir] [options]`; programmatic API; usable in CI and as a pre-push hook.
Input: npm package-lock.json or npm-shrinkwrap.json with lockfileVersion 2 or 3 (the "packages" map). lockfileVersion 1 or unknown => exit 2 with a clear message (v1 lacks the data). yarn.lock and pnpm-lock.yaml are out of scope for MVP (document under Future work; pnpm needs a YAML parser, which would break the zero-dependency rule).
Algorithm:
1. Parse and convert the lockfile into Maps (never trust keys; avoid prototype pollution).
2. For every package entry that declares `optionalDependencies`, resolve each declared name using Node's resolution order inside the lock tree: `<parentPath>/node_modules/<name>`, then each ancestor's node_modules, up to the root. Handle nested and hoisted entries, workspaces and `link: true` entries.
3. Declared optional dependency with NO resolvable lock entry => finding.
4. For resolvable entries, read `os`, `cpu`, `libc` arrays (they may be absent = any; support negations like "!win32") and compute which target platforms each entry satisfies.
Targets: default matrix = linux-x64-glibc, linux-x64-musl, linux-arm64-glibc, win32-x64, darwin-arm64, darwin-x64 (configurable with `--targets` and config; presets such as `github-actions` and `common-dev`; allow narrowing to the platforms the user actually uses).
Rules:
- LM001 (error): parent declares an optional dependency that is missing from the lockfile (pruned). Show parent, missing name, and the platform inferred from the name suffix ONLY as a labeled heuristic ("inferred").
- LM002 (error): for a "platform-variant group" (a parent whose optional deps carry os/cpu/libc), none of the present entries satisfies a requested target platform.
- LM003 (warn): all platform-specific entries across the whole lockfile cover exactly one os/cpu pair => lockfile was probably generated on a single machine.
- LM004 (info): summary matrix (rows = variant groups, columns = targets, cells = present/missing).
Remediation text: print a short, accurate explanation and suggested steps, labelled "verify before running". Do not claim a fix works unless Phase 0 confirmed it. Never modify files. No --fix in MVP.
Optional `--verify-with-npm` (off by default): copy ONLY package.json and the lockfile into a temp directory, run `npm ci --dry-run --ignore-scripts` with the `--os`, `--cpu`, `--libc` flags for each target (first confirm those flags exist in the installed npm; otherwise skip with a message), and compare with lockmatrix's result. Clean up the temp dir.
Output: human (colored only if TTY and NO_COLOR unset), `--format json`, `--format github` (annotations), `--format sarif`. Exit codes: 0 clean, 1 findings at/above `--fail-on` (default error), 2 usage/runtime error.
Config: optional `lockmatrix.config.json` (strict schema validation with clear errors): `targets`, `ignorePackages` (each with required reason), `failOn`.

## 5. Security requirements (implement AND test)
- Lockfiles are UNTRUSTED input (pull requests from forks). Enforce a max file size (default 100 MB) and a max package-entry count; fail gracefully.
- Never touch the filesystem using paths taken from the lockfile; lock keys are only used as Map keys.
- Prototype-pollution safe (Map / Object.create(null); test keys like "__proto__", "constructor", "prototype").
- Output injection: strip ANSI/control characters from package names and strings before printing; escape GitHub workflow-command syntax (%, \r, \n, ::) in annotations; escape SARIF/JSON properly. Test with malicious names.
- ReDoS-safe: no backtracking-prone regexes on untrusted strings; test with adversarial inputs under a time limit.
- If --verify-with-npm is used: execFile (never exec / shell: true) with argument arrays, timeouts, max buffers, temp dir with restricted contents, always cleaned up. Handle Windows npm.cmd safely (Node's 2024 hardening forbids spawning .cmd without a shell; resolve npm via `npm_execpath` or run npm-cli.js with process.execPath) and test that logic.
- No eval/Function, no dynamic require of user input, no network calls outside verify mode.
- SECURITY.md with private vulnerability reporting via GitHub Security Advisories.
- Supply chain: no runtime deps, `npm audit` clean, lockfile committed, GitHub Actions pinned to commit SHAs with least-privilege `permissions:`, Dependabot (actions + npm), CodeQL workflow, publishing via GitHub Actions with `--provenance`, `"files"` allowlist (verify with `npm pack --dry-run`).

## 6. Testing requirements
- `node:test`. Hand-written small lockfile fixtures (v2 and v3) shaped like real rollup/esbuild/swc/lightningcss/sharp/fsevents data from Phase 0: complete lockfile, mac-only lockfile, linux-only lockfile, musl/glibc variants, negated os values, missing os/cpu/libc fields, nested and hoisted optionals, workspaces, link entries, empty lockfile, lockfileVersion 1, malformed JSON, BOM/CRLF, duplicate keys.
- Property-based style tests (hand-rolled generator, no libraries): random lock trees must never crash and results must be deterministic regardless of key order.
- Fuzz: garbage and truncated JSON must produce exit code 2, never an unhandled exception.
- Performance test: synthetic lockfile with 50,000 packages analyzed in a few seconds; assert a generous time limit.
- Security tests from section 5 (malicious names, prototype keys, oversized input, control characters in output, annotation injection).
- Every output format snapshot-tested; exit codes tested; CLI end-to-end tests run the real binary.
- Verify-mode tests use a fake npm executable on PATH (no real network), plus a test that proves no files outside the temp dir are touched.
- Coverage: `node --test --experimental-test-coverage`, enforce >= 90% line coverage in CI.
- CI matrix: ubuntu, windows, macos x supported Node versions; jobs for lint, typecheck, pack-content check, a smoke test that installs the packed tarball into a clean folder, and dogfooding (run lockmatrix on its own repo lockfile).
